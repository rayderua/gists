# kubenv

Each terminal gets its own kubectl context and namespace: switching to `prod`
in one terminal doesn't switch the others. Cluster configs are kept as one
file per context in `~/.kube/config.d/` and merged into `~/.kube/config`.

Requirements: bash, kubectl. Run `kubenv help` for all subcommands.

## How it works

```
~/.kube/config.d/*.yaml  --merge-->  ~/.kube/config  --copy on shell start-->  ~/.kube/kubenv/kubenv.<host>.<pid>.*
   (source of truth)                  (generated)                               (this terminal's KUBECONFIG)
```

- When sourced, kubenv copies `~/.kube/config` into a temp file for this
  shell and exports `KUBECONFIG` pointing to it. Everything you change in this
  terminal (`kubenv ctx`, `kubenv ns`, `kubectl config ...`) changes only that
  copy.
- A new terminal starts on an empty `null` context on purpose, so a command
  never runs against a cluster you didn't pick.
- The temp file is deleted when the shell exits. Files of shells that died
  without cleaning up are removed by the next shell that starts (or by
  `kubenv clean`).

## First run

If you already have a `~/.kube/config` with several clusters, split it once:

```bash
kubenv split      # writes ~/.kube/config.d/<context>.yaml for every context
```

`/` and `:` in context names (EKS ARNs) become `_` in file names.

## Everyday use

```bash
kubenv ctx                # list contexts, * marks the current one
kubenv ctx prod           # switch this terminal to prod
kubenv ns monitoring      # switch namespace
kubenv ctx -              # back to the previous context (also: kubenv ns -)
kubenv ctx cur            # print the current context
```

## Adding or changing a cluster

Changes stay in the current terminal until you save them.

```bash
aws eks update-kubeconfig --name prod   # or any tool that writes $KUBECONFIG
kubenv save                             # store the current context in config.d and rebuild ~/.kube/config
```

`save` writes the current context into every file in `config.d` that already
has it, or into a new `<context>.yaml`. To add a config file you got from
someone, drop it into `~/.kube/config.d/` and run `kubenv merge`.

Other terminals keep their copy; run `kubenv reload` there to pick up the new
`~/.kube/config`.

## Safety nets

- `merge` and `save` refuse to rebuild `~/.kube/config` if a context would be
  lost: one that is in `~/.kube/config` but in no file in `config.d` (not
  split yet, or added by a tool running outside kubenv). Add it with
  `kubenv split`, or drop it with `kubenv merge force`.
- Before every `merge`, `save` and `restore`, `~/.kube/config` is backed up
  to `~/.kube/kubenv/backups/`:

  ```bash
  kubenv restore list       # backups, newest last
  kubenv restore            # back to the latest one
  kubenv restore config.20261022-222612
  ```

  The current config is backed up before a restore, so a second `restore`
  undoes the first.
- Files in `config.d` and backups are created with mode 600: they hold
  credentials.

## Settings

Set before sourcing the script:

| Variable | Default | Meaning |
|---|---|---|
| `KUBENV_BACKUPS` | `10` | How many backups to keep |
| `KUBENV_CLEANUP_AGE_MIN` | `1440` | Age (minutes) after which temp files that can't be checked by PID are removed: old-style names, or another host sharing `$HOME` |

## Files

| Path | What |
|---|---|
| `~/.kube/config.d/*.yaml` | Your cluster configs, one per context |
| `~/.kube/config` | Generated by `merge`/`save`; don't edit by hand |
| `~/.kube/kubenv/kubenv.<host>.<pid>.*` | Per-terminal copies |
| `~/.kube/kubenv/backups/` | Backups of `~/.kube/config` |
